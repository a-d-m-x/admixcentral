# AdmixCentral security audit — 9 September 2026

Repository: `/home/baga/Code/admixcentral`  
Starting revision: `8b85fe57620b640ba7d73973d58006088f9cbfe1`  
Status: source fixes applied locally; deployment and infrastructure remediation remain.

The review found an authenticated command-injection path to managed pfSense firewalls, authorization gaps, credential disclosures, browser injection, and missing transport authentication. The confirmed application issues described below have been patched. This is **not a clean bill of health for a deployment**: the privileged installer configuration and unsigned updater remain material risks, with remediation methods below. A source review cannot establish that no exploitable defects exist.

Native pfSense/OPNsense certificates remain supported. AdmixCentral can explicitly trust each firewall's HTTPS public key; a public CA is unnecessary. See the [deployment and certificate guide](/home/baga/Code/admixcentral/docs/SECURITY_DEPLOYMENT.md).

## Scope and evidence

Repository-wide searches covered application code, routes, middleware, policies, Blade/JavaScript, jobs, configuration, migrations, dependency locks, installers, upgrade scripts, and release automation. Targeted manual tracing covered request-to-command paths, tenant and role checks, outbound HTTP/SSH, certificate handling, uploads/restores, setup, authentication, and secret rendering. Searches also covered SQL/raw queries, process execution, deserialization, XML parsing, archive extraction, filesystem writes, and browser HTML/JavaScript sinks. Dependency advisories were queried for the locked Composer and npm dependencies. A limited tracked-file scan for recognizable private keys and token formats found no matches; it was not a full Git-history or entropy-based secret audit.

Tests ran in isolated copies with a synthetic application key, SQLite in memory, fake mail/queues and synthetic credentials. Harmless local command probes used stub functions; no exploit command was sent to a firewall. TLS behavior was exercised against an ephemeral HTTPS listener on 127.0.0.1. This was not a live network penetration test or a review of deployed firewall firmware. During baseline testing, some existing incomplete HTTP mocks permitted real requests toward their hardcoded private fixture addresses. The patch makes unexpected Laravel HTTP requests fail during tests and repairs those mocks; the final suite is isolated.

Evidence directory: [security-audits/admixcentral-2026-09-09](/home/baga/VMs/security-audits/admixcentral-2026-09-09). Evidence contains synthetic probes, not production credentials.

## Remaining risks and concrete remediation methods

### R01 — Privileged web-service sudo rights (high; root escalation after a web-process compromise)

Affected source includes [install_admixcentral.sh](/home/baga/Code/admixcentral/install_admixcentral.sh:899), [upgrade_admixcentral.sh](/home/baga/Code/admixcentral/upgrade_admixcentral.sh:275), [scripts/install.sh](/home/baga/Code/admixcentral/scripts/install.sh:197), and [scripts/setup-ssl-permissions.sh](/home/baga/Code/admixcentral/scripts/setup-ssl-permissions.sh:17).

These grant the web runtime broad `certbot`/`nginx` execution and/or the ability to replace supervisor and PHP-FPM configuration followed by service reloads. Restricting the destination filename does not make attacker-controlled configuration safe. Certbot explicitly supports shell hooks; broad root access to it is a root execution capability. See [Certbot hook documentation](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates).

**Immediate deployment method:** run certificate provisioning and performance tuning outside the web app, under an operator/deployment account. Back up the relevant sudoers drop-in outside `/etc/sudoers.d`, remove the web-runtime grants with `visudo`, and validate with `visudo -c`. Confirm with `sudo -l -U <runtime-user>` that no equivalent grant exists elsewhere. Web SSL installation/tuning will cease to work until a safe replacement is provided; firewall management itself does not require these root grants. Make the same change to all installer/upgrade paths before rerunning them, otherwise they reintroduce the permissions.

**Application method:** replace these grants with a root-owned helper outside the web-writable tree. Accept only bounded scalar operations such as a validated hostname or worker count; construct the entire configuration inside the helper. Do not accept shell commands, hook strings, arbitrary paths, configuration text, web-writable templates, or caller-created temporary files. Validate and atomically install the generated config before reloading a fixed service. Run workers/FPM as unprivileged users. This design has not been implemented or live-tested in this patch.

### R02 — Unsigned self-update installation (high supply-chain risk)

[SystemInstallUpdate.php](/home/baga/Code/admixcentral/app/Console/Commands/SystemInstallUpdate.php:108) explicitly skips verification, downloads a GitHub tag source archive, overlays application files and then runs migrations. Release signing in [.github/workflows/release.yml](/home/baga/Code/admixcentral/.github/workflows/release.yml:67) is commented out. HTTPS to GitHub does not authenticate the release against an independently managed signing key. Exploitation requires control of the consumed release source or equivalent update input; no unauthenticated update-trigger bypass was demonstrated.

**Immediate deployment method:** block `/system/settings/updates/install` at the reverse proxy and stop using `php artisan system:install-update` (including `--force`). Deploy reviewed commits through a separate deployment account. For nginx, add `location = /system/settings/updates/install { return 403; }` inside the central HTTPS server, then validate/reload nginx as an operator. This is a containment method, not an implementation of signed updates.

**Code method:** publish the exact `update.zip` asset whose SHA256 appears in a signed manifest; fetch that asset, the manifest and its detached signature. Verify the manifest with a root/deployment-owned pinned minisign public key outside the writable application directory. Require the requested version, expected asset identity and SHA256 to match; enforce size/uncompressed-size limits and reject symlinks/path traversal. Only then extract into a fresh staging directory. Deploy atomically, run checks/migrations under the intended limited account and retain a rollback release. Remove the bypass option. Do not compare the release asset's hash against GitHub's independently generated source zip. Signing-key provisioning and the release pipeline change remain outstanding.

### R03 — Multi-tenant outbound network access / DNS rebinding (medium–high, topology dependent)

AdmixCentral must reach private firewall addresses. A universal private-address ban would defeat that purpose. Current URL checks occur when a firewall is registered/edited; a later DNS resolution can differ. Tenant administrators can still select reachable HTTPS destinations. The proxy-check endpoint also needs network-level containment despite redirects being disabled.

**Immediate deployment method:** put Central and its workers in a management network with egress limited to approved firewall management IPs and ports, plus separately approved DNS/mail/update services. Block cloud metadata, unrelated loopback services and unrelated tenant networks at the host/container/network boundary. Allow rules must cover both IPv4 and IPv6. Prefer isolated per-tenant workers or tunnels where tenants must not reach each other's management networks.

**Code method:** maintain an operator-approved destination/port allowlist per tenant. At connection time resolve all addresses, reject prohibited or unapproved results, fail closed on resolution failure, and connect to the approved address while preserving the original TLS name (for example cURL `CURLOPT_RESOLVE`). Repeat this for every request, pool, provisioning flow, backup and proxy test; do not only validate the initial form. Explicit TLS/SSH key trust still applies. This connection-address policy is not implemented by this patch.

### R04 — Local production flags and secret-file permissions (high if this configuration is deployed)

The local untracked `.env` declares `APP_ENV=production`, `APP_DEBUG=true`, `SESSION_ENCRYPT=false` and has mode `0644`. Its secret values were not printed. These observations do not establish the settings on another server.

Set `APP_DEBUG=false`, `SESSION_ENCRYPT=true`, `APP_URL=https://<canonical-central-host>` and `SESSION_SECURE_COOKIE=true` on the production host. Set `LOG_LEVEL` to the operational level you need, normally `warning` or `error` for sensitive management traffic. Restrict `.env` and cached configuration to the runtime/deployment identities (e.g. `0640` with an appropriate group or `0600` for a single owner). Rebuild Laravel configuration and restart long-lived workers/FPM using your normal deployment procedure. Changing session encryption can invalidate existing sessions; plan a fresh login. Never regenerate an existing `APP_KEY` casually: encrypted firewall credentials depend on it.

### R05 — Public first-run setup (high on an exposed fresh installation)

The `/setup` form intentionally creates the initial administrator when no user/setup lock exists. A new internet-reachable instance can be claimed by whoever completes it first. Existing populated installations reject setup.

Provision behind an administrative VPN or a loopback-bound listener/SSH tunnel and complete setup before exposing the service. For unattended deployments, change `SetupController` to require a cryptographically random bootstrap token generated locally by the installer, stored as a hash outside public assets, verified with constant-time comparison and invalidated on successful setup. A database transaction alone is not an authentication mechanism. No bootstrap-token flow was added here.

### R06 — Backup and session hardening (medium; additional work)

Raw firewall XML backups under private application storage contain firewall configuration secrets. The system-backup format already uses authenticated AES-GCM for new exports, but its legacy CBC import fallback lacks an authentication tag. Store raw firewall backups on encrypted storage with runtime-only access and retention limits; for portable encryption, use authenticated encryption with keys separated from backup storage. Restrict legacy CBC restoration to an offline migration tool, then re-export in the authenticated format. The normal web restore path should eventually reject legacy unauthenticated files.

The authenticated route group does not currently use Laravel's `auth.session` middleware. Add and test session invalidation for password resets, credential changes and administrative account revocation; ensure a previously issued session cannot survive the revocation policy. Require two-factor authentication for central administrators where operationally feasible. These are remaining hardening items, not demonstrated authentication bypasses in this review.
